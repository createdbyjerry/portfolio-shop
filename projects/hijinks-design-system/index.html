Hijinks Design System

Turning documentation into a living product

Geospan’s platform, from 3D roof purchasing to estimation tools and analytics dashboards, ran on documentation nobody trusted. In 2024 I led the work to turn it into a living product: one searchable home for components, patterns, accessibility rules, token mappings and the reasons behind each decision. In 2026 I rebuilt the Figma library on variables to show how I’d run it today.

01 / The Problem

Fragmented blueprints, wasted sprints

With no single source of truth for UI patterns, Geospan spent product time on repeat work:

Docs nobody trusted

Component pages were inconsistent, incomplete and disconnected from live code, so engineers guessed during implementation.

No record of “why”

Designers and PMs had no record of design rationale, so teams forked patterns they didn’t understand and created duplicate components.

The onboarding tax

New designers and engineers took weeks to find their footing, and often rebuilt legacy patterns by accident.

Why it mattered

Every sprint spent rebuilding buttons and form fields was a sprint not spent on hard spatial problems like 3D roof modeling. The goal was to make the right design choice the easiest one.

02 / The Solution

The blueprint framework

We treated documentation as a product. Every component page follows the same five-part blueprint:

Step 01

Purpose

When to use it, and why it exists.

Step 02

Anatomy

The component’s structural zones and every state.

Step 03

Tokens used

The exact color, spacing and type tokens it uses.

Step 04

Accessibility

Keyboard, screen-reader and contrast rules.

Step 05

Do / Don’t

Side-by-side examples of correct and incorrect use.

The quick-start engine

Checklists and task guides for Geospan’s most complex, most frequent work, such as editing vector map components and styling spatial map layers.

Three-tier tokens, in sync

Core, semantic and component tokens, synced between Figma and code by an automated pipeline. The top 20 highest-traffic components were rebuilt on it first.

Research, audit, pilot, roll out

04 / Decisions

The calls that shaped the system

Build on Joy UI, not from scratch

Engineering already shipped Joy UI. Mapping every Figma component to Joy’s variant, color and size props meant design matched code by default. The tradeoff: we inherited Joy’s constraints, and Geospan-only pieces like the VChip data chip lived in their own layer.

Pilot 20 components, not 40

The highest-traffic components carried most of the duplication. Proving the template there earned buy-in before we scaled it to the rest.

Deprecate, don’t delete

Variants like Button Soft and Solid Success stayed in the library, marked deprecated, so existing screens kept working while new work moved to the supported set.

The same five questions on every page

A fixed template made pages slower to write but much faster to read. Engineers learned exactly where each answer lives.

05 / Impact

Seamless alignment

Treating documentation as a product changed how Geospan built UI:

Reimplementations cut

Duplicate component builds and accidental UI rebuilds fell about 60% within two quarters, tracked through pull request review tags.

Accessibility by default

Accessibility rules sat on every component page, so they were applied during design instead of caught in QA.

One workspace

Designers and engineers stopped bouncing between disconnected files and worked from one synchronized pipeline.

06 / If I built it today

The 2026 rebuild

The 2024 fundamentals held up, but the Figma library had drifted. In 2026 I decoded the original file, audited it, and rebuilt it with a Figma plugin I wrote that generates the whole library: variables, styles, components, docs pages and the images below. The visuals in this section come from that rebuild.

14 → 4

variable collections: Primitives, Theme, Size, Component

78 → 12

text styles, three font families down to one

1,631 → 90

variants across eight rebuilt component families

60/80 → 120/120

text pairs passing WCAG AA, plus a High-contrast mode at AAA

Three tiers, three modes

Primitives feed Theme roles, which feed Component tokens. Light, Dark and a new High-contrast mode replace the “Dark Mode” variant that six component sets used to carry.

Size is a mode, not a variant

Components read height, padding and type size from a Size collection. Tooltip went from 195 variants to 4, Button from 180 to 48.

Contrast fixed at the source

Amber and yellow text failed on white. Solid buttons now carry dark text, and the focus ring was darkened from 2.4:1 to 5.3:1.

07 / AI-ready

Tokens agents can read

A tokenized system is what keeps AI-generated UI on-brand. The rebuild is set up for it:

Standard token format

The plugin exports variables as W3C DTCG JSON, with modes and code syntax, ready for Style Dictionary.

Code names in Figma

Every color carries its Joy CSS variable, so Dev Mode shows var(--joy-palette-primary-solidBg), never a hex value.

Rules an agent follows

A short guidelines file covers what humans learn from the docs: no raw hex, one Solid Primary per view, and status never shown by color alone.

08 / Retrospective

Lessons and what’s next

The hard lesson

Documentation dies in a silo. Guidelines have to live inside the tools teams already use, like Figma libraries and Jira tickets, so nobody goes hunting for answers.

What’s next

The 2024 plan was analytics on the docs pages. The rebuild adds the next step: Code Connect from each Figma set to its Joy component, and the Figma MCP server so coding agents build with the system instead of around it.
